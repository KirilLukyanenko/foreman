# Localization eval

Does Foreman find the code a task is about? Ten real GitHub issues, each fixed by a merged PR: the repository is
checked out at the commit before the fix, the issue's title and body are the task, and the **gold** files are the
non-test source files the fix changed. A method scores by where it ranks the gold files.

`cases.json` lists the cases (repository, issue, fix, base commit, gold files). Issue texts are not stored here:
`foreman eval localization` fetches them with `gh` at run time into the job folder.

```bash
dotnet run --project src/Foreman.Cli -- eval localization             # no model: BM25 and the code map variants
dotnet run --project src/Foreman.Cli -- eval localization --readers   # plus the dossier's task reader
```

Results: [results.md](results.md) (regenerated by each run; `results.json` has every rank).

## What the numbers can and can't say

- **Ten cases, one run each.** Enough to see a difference of 0.38 vs 0.90 MRR, not to rank close methods. Model
  runs vary (the same reader on the same repository has cost $0.37 and $0.63); the next step is 3 runs per case
  with intervals, as `docs/architecture.md` plans for every eval.
- **Contamination.** The fixes are public and from 2024–2026; a model may have seen them in training and
  "remember" where the fix went. The no-model methods can't. A clean comparison needs issues fixed after the
  model's training cutoff (SWE-rebench's approach).
- **Gold is what the PR changed**, not what was strictly necessary. Two misses of the reader (MediatR's and Hono's
  second files) are files the PR touched alongside the main one.
- Small repositories (5–15 files) make every method look good; the medium ones (Polly, FluentValidation, MediatR,
  Hono, rich) are where methods separate.
